# Mobile

**Principle:** a small screen forces trade-offs, and usability must not be the thing traded away. The same rules apply with less room.

Check on a real phone or at a phone-sized viewport (about 390 px wide).

| ID | Check | How to check |
|---|---|---|
| M1 | Every core task can be completed on a phone | Run the top three tasks end to end. Nothing is desktop-only |
| M2 | Space was saved by prioritising, not by hiding | Things users need often are close at hand. Rare things may be a few taps away, with an obvious path |
| M3 | Features are discoverable | Nothing important depends on a hidden gesture alone: swipe, long-press or shake has a visible alternative |
| M4 | Affordances survive without a cursor | Tappable things look tappable. Nothing needs hover |
| M5 | Tap targets are big enough | About 44 by 44 px, with space between neighbours |
| M6 | Text is readable without zooming | Body text about 16 px. No horizontal scrolling |
| M7 | Zoom is allowed | The viewport tag has no `user-scalable=no` and no `maximum-scale=1` |
| M8 | It is fast on a mid-range phone on mobile data | Measure with throttling. Heavy images and scripts are the usual cause |
| M9 | A deep link opens the deep page | A shared or searched link to an article does not land on the mobile home page |
| M10 | The user can reach the full version | Anything missing from the small layout is still reachable |
| M11 | Typing is kept to a minimum | Right keyboards, autofill, pickers and sensible defaults |
| M12 | It works in both orientations and with the keyboard open | The focused field and the submit button stay reachable |

For native apps, add: the app is learnable in the first session without a tutorial, and what was learned is easy to remember on the next visit.

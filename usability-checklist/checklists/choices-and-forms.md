# Choices and forms

**Principle:** the number of clicks matters less than how hard each one is. Every choice should be mindless and unambiguous.

| ID | Check | How to check |
|---|---|---|
| F1 | Every choice is unambiguous | The user never wonders "is it under A or B?" Options do not overlap in meaning |
| F2 | The form asks only for what it needs now | For each field, ask what breaks if it is removed. Nothing breaks: remove it or move it to later |
| F3 | Optional fields are marked, and few | Required is the default. Optional fields say so |
| F4 | Input is accepted in any reasonable format | Phone numbers with spaces or dashes, card numbers with spaces, dates typed naturally. The code normalises, the user does not |
| F5 | Every field has a visible label that stays visible | A placeholder is not a label. It vanishes on typing |
| F6 | Odd-looking requests are explained in a few words | "We use your phone only for delivery updates" next to the field |
| F7 | Guidance appears where it is needed | Password rules sit by the password field, shown before the first attempt. Brief, timely, hard to miss |
| F8 | Errors name the field and the fix, in plain words | "Enter a date like 14/03/1990", shown next to the field. Not "Error 422" |
| F9 | An error never destroys what the user typed | Submit with one bad field. Everything else is still filled in |
| F10 | Long flows show where the user is | Step 2 of 4. The user can go back without losing data |
| F11 | The right input type is used | Email, phone, number and date fields trigger the right keyboard and autofill |
| F12 | No dead ends | Every screen in the flow has an obvious way forward and a way back |

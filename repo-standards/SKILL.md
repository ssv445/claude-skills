# Repo Standards — installer

Installs a rulebook plus local enforcement into ONE repo. Opt-in per repo: never install without the user asking. Once installed, the repo's hooks enforce it; this skill is no longer needed to run it.

The installed rules exist so that AI agents decide for themselves whether to approve and ship: when every gate passes, `bin/ship` approves and merges with no owner in the loop; with `APPROVER="agent"` (default in `.standards/config.sh`) agents also approve gate-file changes and blast-radius specs — a gate-file change after an extra gate-change review and one plain-English line in `docs/rule-changes.md` — and the owner only answers `owner-review: required` questions on big calls (the agent closes each flag as answered) and reads what agents decided and logged; with `APPROVER="owner"` the owner also approves gate-file changes (`bin/approve <pr>`) and blast-radius specs (`spec-approved`).

What gets installed (sources in this skill folder):

| Source | Installed at | Purpose |
|---|---|---|
| `templates/repo-standards.md` | `docs/guidelines/repo-standards.md` | The rulebook agents follow per issue |
| `templates/claude-md-block.md` | appended to `CLAUDE.md` between its markers (`AGENTS.md` symlinked to it) | Always-loaded pointer + hard rules; only this block is a gate file |
| `templates/spec.md`, `templates/decisions.md`, `templates/adr.md` | `docs/templates/` | Per-issue spec, decision log, ADR |
| `templates/review-checklist.md` | `docs/templates/review-checklist.md` | What reviewers check per gate; the author runs it first |
| `templates/product/{goals,assumptions,stack,roadmap,ideas-rejected}.md` | `docs/product/` | Goals, assumptions, tool stack, dependency-aware roadmap |
| `templates/product/review.md` | `docs/templates/review.md` | Monthly product review |
| `templates/doc-map.txt` | `docs/doc-map.txt` | Code path → doc that must change with it |
| `templates/rule-changes.md` | `docs/rule-changes.md` | Owner's log of rule changes, one line each, append only |
| `templates/seed-profile.md` | `docs/seed-profile.md` | Aggregate-only prod shape for seed generation |
| `templates/github/` | `.github/` | Issue form + PR template (evidence table on top, screenshots attached) |
| `templates/user-stories/README.md` | `docs/user-stories/README.md` | Optional: stable story ids, Given/When/Then, "Covered by" checked by `stories.sh`. Install when the repo has user-facing behaviour worth a story per behaviour; your call, logged in the install's `decisions.md` |
| `scripts/` | `.standards/` | Hooks, gate checks, `config.sh`, `VERSION` (this skill's version) |

| `templates/claude-settings.json` | merged into `.claude/settings.json` | Guard hook blocking gate bypass |

## Steps

1. **Survey.** Read the repo's `CLAUDE.md`, package manifests, test runner configs, existing hooks (`.husky/`, `core.hooksPath`), existing `docs/`. Done when you can name: language/stack, lint, typecheck, unit-test, coverage, e2e, perf commands (or that one is missing), the hook manager in use, the GitHub owner login, and that `jq` is installed (`command -v jq`; the guard hook and `bin/ship` need it — without it the guard blocks every command in the repo but exactly `brew install jq` / `sudo apt-get install -y jq`).
2. **Branch.** Work on `chore/<issue>-repo-standards` (open the issue first; this install is itself an issue). Never on main.
3. **Copy** every row of the table above (copying `scripts/` writes `.standards/VERSION`). Existing files with the same path: merge, never overwrite — show the user the conflict if a merge is not obvious. Append `claude-md-block.md` whole, `<!-- repo-standards:begin -->` and `<!-- repo-standards:end -->` included; on an upgrade, replace only the text between them. An existing `CLAUDE.md` that holds facts (architecture, folders, commands) keeps them outside the markers: only the block is a gate file, so PRs that update the facts stay ordinary changes.
4. **Fill `.standards/config.sh`.** Every command variable set to a real command or left empty with a `# N/A — reason` comment. Empty `UNIT_CMD` or `DIFF_COVERAGE_CMD` is not allowed when the repo has source code: add the tooling instead (e.g. vitest/jest coverage + `diff-cover` for lcov/cobertura). If the repo has two halves with their own tooling (an app and a website, a service and a frontend) or a lot of docs-only branches, also set the optional **change class** (`SITE_*_CMD`, `SITE_TEST_FILES_CMD`, `SITE_E2E_CMD`, and the path lists `SHARED_GLOBS` / `APP_GLOBS` / `SITE_GLOBS` / `DOCS_GLOBS`): a docs-only or site-only branch then skips the checks it cannot affect, and each gate prints what it skipped. List in `SHARED_GLOBS` every file one half's tests read from the other, and set `CROSS_READS_APP_FILES` / `CROSS_READS_SITE_FILES` so `cross-reads.sh` catches a new such read. Leave all of it empty for a single-part repo: every check then runs on every branch. Set `BEHAVIOR_DOCS_GLOBS` to any markdown that drives behaviour (runtime prompts, agent commands outside `.claude/`), so a branch editing it never takes the docs-only lane. Set `DEPS_LINKS` to every dependency directory the tests need in the TDD scratch checkout (nested paths such as `site/node_modules` work). Decide whether shell scripts count as source: if `scripts/` (or `bin/`, `tools/`) holds logic the product or its tooling relies on, add it to `SRC_GLOBS` so TDD and coverage reach it, and add `shellcheck` to `LINT_CMD` (it catches bash 3.2 breakage such as `mapfile` or `${x,,}` on macOS); a script left out of `SRC_GLOBS` escapes every check but lint. If the repo has invariant guard scripts (`scripts/guard-*.sh` and the like), set `GUARDS_CMD` to run them all (and `GUARDS_PART` if they must run on docs branches too). Set `TDD_COMPILE_FAIL_RE` for a compiled or type-checked test runner (e.g. `Cannot find module|cannot find .* in scope|error TS2305`), so a test whose only red is a compile error is labelled. Set `MERGE_MODE` to how the repo merges today (`squash`, `merge` for step-split commits, `rebase`). If the repo has a UI, set `UI_GLOBS` to its UI files, so a PR changing them needs a screenshot in its body (`EVIDENCE_MAX_KB` caps images committed under `docs/work/`), and set `EVIDENCE_CMD` to the repo's one evidence script: it captures the standard set (each supported viewport in each theme) from the app running locally into a new temp dir and prints the files, one per line, last. Adopt what the repo has before writing anything: sitaram (`~/www/sitaram/CLAUDE.md`, "Done": 390×844, 360×740 and 844×390 on every theme, saved by `LAYOUT_SHOTS=<dir> node tests/e2e/layout.mjs <url>`) already drives its own browser in its e2e layout check, so its `EVIDENCE_CMD` is a thin wrapper that makes the temp dir, runs that, and lists the files. Read such a script for its viewports, themes and states; copy none of its app specifics. With nothing to adopt, copy `templates/evidence-capture.example.sh` (this skill folder, not installed as is) to `scripts/evidence-capture.sh` and set its pages, viewports, themes and how a theme is applied; run its `--dry-run` to check the plan, then one real run against the dev server. Evidence capture was the largest worker cost before this existed, with every agent improvising its own. If the repo deploys, set `DEPLOY_CMD` (from a clean checkout: install, build, deploy) and `LIVE_CHECK_CMD` (read-only proof production serves the build). Checks only this repo needs go in `.standards/local/pre-push.d/` as executables, never into the standard files. For coverage and single-file test runners per language (TS/vitest, Python, Go, Swift), adapt `recipes/README.md` in this skill folder; it is not installed. Speed, same gates: pre-push runs its independent checks at the same time in lanes (lint, typecheck, unit, site, repo); if two checks write the same files (a shared build dir, one test database), put them in one lane with `PREPUSH_LANES` (e.g. `"typecheck=build unit=build"`; `"*=serial"` for one at a time). If perf has an untimed part (builds, fixture generation, accuracy), split it into `PERF_PREP_CMD`, which runs beside e2e, and leave only the timed part in `PERF_CMD`, which runs alone under a machine-wide lock. Set `E2E_EXCLUSIVE=1` when e2e cannot run twice at once (a fixed port, one simulator). Set the reuse key's inputs outside git first: `VERDICT_KEY_CMD` printing the tool versions e2e and perf depend on (e.g. `node -v && pnpm exec playwright --version`), `VERDICT_IGNORED_GLOBS` for gitignored files tests read (default `.env*`), `VERDICT_ENV` for environment variables they read, and `VERDICT_DEPS_CMD` when the stack has no lockfile or install marker the key already knows. Once those are set, turn on `VERDICT_REUSE=1` when e2e + perf take more than a minute or two: that lets `bin/ship --checks-only` overlap them with the pre-merge review and makes a re-run on an unchanged input cost seconds. This is the agent's call: log it in the install's `decisions.md` with the key inputs chosen, for the owner to revert. Leave it off when a test reads something the key cannot name (a shared service, a database with state). Write the current total to `.standards/coverage-baseline`, rounded down. Leave `APPROVER="agent"` unless the owner has said `owner`; ask it as one of the step-6 gaps, not a separate stop.
5. **Wire hooks.** Install `jq` first if step 1 found it missing, and list it in the repo's setup prerequisites.
   - No hook manager: `git config core.hooksPath .standards/hooks`, and add that line to the repo's setup script / README setup section (it is per-clone).
   - Husky or similar: add a `pre-push` entry that runs `.standards/hooks/pre-push`; leave the manager in charge.
   - The gates of every worktree on the machine coordinate through `STANDARDS_LOCK_DIR` (default `/tmp/repo-standards-locks-<uid>`; nothing to set up). Override it only to another temp dir, the same in every shell: a gate whose lock dir `safe_rm` may not clean refuses to run, and gates with different dirs cannot see each other.
6. **Product context.** First draft `docs/product/` — goals (metric, target, date), non-goals, assumptions, tool stack — from what the repo already shows: code, README, docs, manifests, config, analytics and hosting setup. Then interview the owner, one question at a time, only for the gaps the repo cannot answer (usually targets and dates) and to correct the draft; this one-off context is the only interview. Anything the owner shares that is future work goes to the roadmap Inbox, then through the idea flow in the rulebook (decided and logged by the agent).
7. **Fill the doc map and seed profile** from what the survey found. Doc map: one line per code area that has a describing doc. Seed profile: fields marked `TODO(owner)` where only prod knowledge can answer — list them for the user.
8. **Prove every gate can fail.** On a scratch branch, break each gate once (uncovered line, source change with no test, mapped code without its doc, a planted guard violation, missing decision-log section, failing lint, roadmap item with no goal, a test filter that matches nothing — `TEST_FILES_CMD` / `SITE_TEST_FILES_CMD` given a path with no tests must exit non-zero; with the options set: a "Covered by" naming a missing test, a failing local check, a UI change with no screenshot, a failing `LIVE_CHECK_CMD`) and show the hook output for each failing, then passing after the fix. A gate you could not make fail is not installed — say so.
9. **Report** to the user: what was installed, config values, gates proven (with output), anything left `TODO(owner)` or N/A, the `APPROVER` mode, and the owner's own steps from "Your steps (owner)" in the rulebook. Agent mode (default): only answering `owner-review` questions on big calls (and "merge" where there is no `bin/ship`); everything else is decided and logged for them to read and revert when they choose (`docs/rule-changes.md`, `decisions.md`, `docs/product/`, the monthly review). Owner mode adds: `bin/approve --spec <issue>` for `owner-approval: required` specs; `bin/approve <pr>` for PRs `bin/ship` refuses for a gate-file change or a removed `owner-approval` flag. Open the PR; the owner merges it — on first install there is no `bin/ship` on the base yet, and an upgrade is judged by the base's older rules.

## Upgrade

When the repo already has `.standards/` and this skill is newer than `.standards/VERSION` (no file: installed before versions):

1. **Open an issue and a branch**, like any change. The upgrade changes gate files, so it goes through the gate-change review and one line in `docs/rule-changes.md`, and `bin/ship` judges it by the base's older rules.
2. **Diff** each installed file against this skill's source (the table above). Print the list: unchanged, changed upstream, changed locally, both.
3. **Replace** the standard files with this skill's copies. Never touch `.standards/local/` (the repo's own checks) or `.standards/coverage-baseline`. In `.standards/config.sh`, keep every value the repo set; add only new variables, with their defaults and comments. In `CLAUDE.md` / `AGENTS.md`, replace only the text between the `repo-standards` markers. In `docs/guidelines/repo-standards.md`, replace the whole file: repo additions belong in the repo's own guidelines.
4. **A local edit to a standard file** (both sides changed): move it to `.standards/local/pre-push.d/` when it is an extra check, or to config when a variable covers it; otherwise list it for the owner and keep the skill's copy. Never keep a silent fork: the next upgrade would erase it.
5. **Write the new version** to `.standards/VERSION` (copying `scripts/` does it), run step 8's failure proofs for every gate the upgrade changed, and report what changed in one line each.

## Rules for this skill

- Lean: pre-push must stay ≤ 2 min on this repo. Measure it in step 8; if over, move the slowest check to `bin/ship` and say so.
- The rulebook template is the single source of truth. Repo-specific additions go in the repo's own guidelines, not by editing the installed rulebook — so a later re-install can diff cleanly.
- Self-test of the scripts lives in `tests/run.sh` in this skill folder; run it after changing any script.
- A change to `scripts/` or `templates/` bumps `version:` above and `scripts/VERSION` together; `tests/run.sh` fails when they differ.
- The skill's own scripts delete only through `safe_rm` in `scripts/lib/common.sh`, never a bare `rm` with a variable or relative path; `tests/run.sh` lints `scripts/` for it.
